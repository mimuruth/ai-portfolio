## Engineering Lab 8 — Latency budgets and graceful degradation from scratch

### The mental model

A voice assistant is a **relay race**: microphone → ASR → LLM → TTS → speaker. The
user hears nothing until the last runner crosses the line, so the total time is the
**sum of the legs**, not the average. A slow leg cannot be "averaged away" — it
delays the whole race. Resilience means every runner has a substitute ready
(fallback) and a whistle that stops a stalled runner (timeout) so the baton keeps
moving.

### Mathematical formulations

**Latency budget.** With per-stage latencies $$T_{\text{ASR}}, T_{\text{LLM}},
T_{\text{TTS}}$$ and overhead $$T_o$$, the mouth-to-ear delay is

$$T_{\text{e2e}} = T_{\text{ASR}} + T_{\text{LLM}} + T_{\text{TTS}} + T_o.$$

The measured demo baseline sums to $$61.8 + 93.0 + 46.9 \approx \mathbf{202}$$ ms at
p50 — and the LLM leg dominates, so that is where optimisation pays.

**Little's Law.** For a stable queue, the average number of in-flight requests
$$L$$, arrival rate $$\lambda$$, and time-in-system $$W$$ satisfy

$$L = \lambda\,W.$$

If work arrives faster than it drains ($$\lambda W$$ exceeding your concurrency
budget), the queue grows without bound — which is why a real-time system uses a
**bounded** queue and **sheds load** rather than letting latency climb forever.

### Bare-metal implementation — timeout with fallback

The heart of `resilience.fallback`, standard library only:

```python
from concurrent.futures import ThreadPoolExecutor, TimeoutError as FT

_pool = ThreadPoolExecutor(max_workers=8)

def with_timeout(fn, *args, timeout, fallback):
    """Run fn; if it exceeds `timeout` seconds or raises, return fallback."""
    fut = _pool.submit(fn, *args)
    try:
        return fut.result(timeout=timeout)
    except (FT, Exception):
        return fallback

# every external call plans three outcomes: success, slow (timeout), failure
reply = with_timeout(call_llm, transcript, timeout=1.5,
                     fallback="One moment — let me try that again.")
```

Per-stage timings feed the same `percentile` function from Chapter 5's lab to
produce p50/p90 per stage.

> **EXAMPLE — degraded turn.**
> ```
> ASR ok (62 ms) -> LLM TIMEOUT at 1.5s -> spoken fallback delivered
> user hears: "One moment - let me try that again."   (never dead air)
> ```

> **Production note — barge-in and circuit breakers.** If the user speaks while the
> assistant is talking, **cancel** the current turn immediately and listen — this
> is what makes it feel real. After repeated failures of a dependency, **open a
> circuit breaker**: stop calling it for a cool-off period instead of timing out on
> every request, which would otherwise turn one slow dependency into system-wide
> latency.

### Review & exercises

- **Troubleshooting.** Under load, latency climbs without bound and never recovers.
  Which mechanism is missing — timeout, bounded queue, or circuit breaker — and
  how does Little's Law explain the symptom?
- **Computation.** Requests arrive at $$\lambda = 20/\text{s}$$ and each spends
  $$W = 0.25$$ s in the system. How many are in flight on average? If your
  concurrency budget is 4, what must change?
- **System design.** Specify the three planned outcomes (success, slow, failure)
  for the TTS stage, including the exact user experience of each.
