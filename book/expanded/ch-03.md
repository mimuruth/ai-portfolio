## Engineering Lab 3 — Version control as a safety system

### The mental model

Git is a **save-game system for code**. Every commit is a save point you can
return to; every branch is a parallel save slot where you can experiment without
risking the main file. A pull request is asking a reviewer to look at your save
before it overwrites everyone else's. Branch protection is the rule "you may not
overwrite the shared save unless the automated tests pass."

### First-principles logic — the cost of a leaked secret

Removing a secret from the current file is **not** enough, because Git keeps
history. If a key lived in $$c$$ commits before you noticed, it is recoverable from
all $$c$$ of them — and crawlers scrape public pushes within minutes. The only safe
response is **rotation**: revoke the exposed key at the provider and issue a new
one. The layered defence exists to make the probability of reaching that state as
close to zero as practical: `.gitignore` (never staged) → `.env.example` (shape,
not secret) → gitleaks (scan) → pre-commit (block locally before the commit
exists).

### Bare-metal implementation — a minimal pre-commit secret guard

The repos use gitleaks; here is the *idea* in ten lines of standard-library Python
so you understand what a hook does — a script that exits non-zero (blocking the
commit) if a staged file looks like it holds a key:

```python
#!/usr/bin/env python3
import re, subprocess, sys

PATTERNS = [r"sk-[A-Za-z0-9]{20,}", r"AKIA[0-9A-Z]{16}", r"-----BEGIN [A-Z ]*PRIVATE KEY-----"]
staged = subprocess.run(["git", "diff", "--cached", "-U0"], capture_output=True, text=True).stdout
hits = [p for p in PATTERNS if re.search(p, staged)]
if hits:
    print("BLOCKED: possible secret matching:", hits)
    sys.exit(1)   # non-zero exit aborts the commit
print("no secrets detected")
```

> **EXAMPLE — the hook doing its job.**
> ```
> BLOCKED: possible secret matching: ['sk-[A-Za-z0-9]{20,}']
> ```
> In the real repos, `gitleaks` (pinned v8.18.4 in `.pre-commit-config.yaml`) does
> this far more thoroughly and also scans full history.

> **Production note — green-because-skipped ≠ green-because-passed.** A CI job that
> silently skips (e.g., the eval gate with no `OPENAI_API_KEY`) shows a green check
> but proves nothing. Set the secret so the gate *runs*, and make missing signals
> (a `nan` score) count as failure — Chapter 5, §5.10.

### Hands-on lab

1. In a scratch repo, save the script as `.git/hooks/pre-commit`, make it
   executable, and try to commit a file containing `sk-` followed by 20 characters.
   Confirm the commit is blocked.
2. Install the real tooling: `pip install pre-commit && pre-commit install`, then
   `pre-commit run --all-files`.
3. On a GitHub repo, protect `main`: require a PR and require the `lint-test` and
   `gitleaks` checks. Push a failing change to a branch and confirm the merge
   button is disabled.

### Review & exercises

- **Troubleshooting.** You committed a key, deleted it in the next commit, and
  pushed. Is the repo safe? Explain in one sentence and give the required action.
- **Derivation.** If each of $$k$$ independent layers fails with probability $$p$$,
  the chance a secret slips through all of them is $$p^{k}$$. With $$p=0.1$$ and the
  four layers here, how small is that?
- **System design.** Design the CI checks you would *require* (not just run) before
  allowing a merge to `main` for `prod-rag`, and say what each protects.
