## Engineering Lab 11 — Auditing for "real numbers"

### The mental model

A portfolio repo is judged in **sixty seconds**: README, architecture diagram, a
results table with numbers, green CI. The difference between a tutorial and a
portfolio is items 10–11 of the checklist — **real benchmarks** and an **evaluation
report**. A reviewer's first probe is "is this real?"; a repo that answers with
`faithfulness 0.87`, `89.6 tok/s`, `p50 2.3 s`, `$0.00025/request` has already won
that argument.

> **Production note — distinguish ◐ from ○.** A ◐ item is *done but needs a manual
> activation* (set the CI secret; run the Langfuse stack; add provider keys). A ○
> item awaits a resource (a GPU run). Neither is missing engineering — say so
> plainly in the README rather than hiding the gap.

### Hands-on lab

1. Open one repo and score it against the 17-item checklist in §11.1. Mark each
   ✅ / ◐ / ○.
2. For every ◐, write the one command that activates it (e.g.,
   `gh secret set OPENAI_API_KEY --repo mimuruth/prod-rag`).
3. Confirm the hub's "results at a glance" table matches the numbers in each repo's
   README — inconsistency is the fastest way to lose credibility.

### Review & exercises

- **Troubleshooting.** A reviewer says your benchmark "isn't reproducible." Which
  three facts, from the Chapter 6 / Appendix A methodology, are you probably
  missing from the results file?
- **System design.** Draft the one-paragraph "Known limitations" section for
  `prod-rag` — honest, specific, and framed as next steps rather than apologies.
